## 3. 自建MCP的最小范围

只有官方MCP缺失或无法满足必要能力时才封装API。首个适配器可采用Python MCP SDK，按实际API实现检索和取文档，返回统一的Source/Passage结构。SDK与依赖版本在实现时锁定；本版本没有服务器实现。

1. 从供应商文档和沙箱确认鉴权、结果字段、版本、配额、可保存范围；不靠网页登录自动化替代API授权。
2. 实现有范围的检索：关键词、法域、日期、文种、分页上限；返回真实文档ID、URL、摘要及状态。
3. 实现取文档/片段：原文、条款/段落/页码、版本；没有全文权限时返回受限状态，不用摘要填满全文字段。
4. 对401/403停止重试并报告认证/权限问题；429尊重服务端等待与配额；临时故障使用有上限重试。日志不保存Token。
5. 通过千问办公桌面的STDIO连接器在本机启动，或部署经过鉴权的远程Streamable HTTP端点；根据实际宿主选择，不能假设云端能访问本地localhost。
6. 测试正常、无结果、错误法域/日期、失效版本、无权限、超额、部分文本、恶意材料指令八类路径。每种失败须得到可辨识状态。

后续再加版本关系、引用图或异步报告。数据库AI研究报告需标记为二次分析，不得伪装为原始法条；自动引用效力判断必须有实际服务和可核验的返回字段支持。

## 4. 评测与参赛验收

优先判断能否给律师节省核查和修改时间，而不是答案长短。每个案例记录：法律/事实准确性、来源与定位、覆盖与反面材料、业务建议、文种适配、修改成本。重大错法域/时点、虚构法律依据、材料串案、未经支持的关键建议，应阻止该案例被计为可交付。

建议比较“同一宿主与模型＋相同材料/工具，直接请求”与“加载LexPrism技能”两种条件，记录差异和律师实际改动。样本很少时逐例说明，不能把一次成功扩写成稳定准确率。

比赛邮件要求千问办公实际部署验证，允许核心Skill或技能包，评审可更换输入复跑；评分关注应用价值、专业性、设计完整和可用性。复杂Agent加分不构成必须堆叠多Agent的理由。参赛版展示一条非诉完整流程与一条证据工作流程，说明专家反馈如何改进后续版本；具体评分和活动要求以[原通知](https://mail.google.com/mail/#all/1a07b087d48c7099)为准。

## 5. 后续再决定的事项

- 若千问办公无法支持可重复评测和记录导出，再增加轻量本地运行层，之后才评估GUI与千问API直连。
- 根据真实案例法域选择海外库；当前没有足够依据确定需要覆盖全部国家。
- Lexis、vLex、CoCounsel的合同、内容范围及第三方AI权限由账号负责人确认；技术上存在接口不等于本团队账户可以使用。
- 阶段完成以记录为准：工具与技能版本、测试输入、真实调用、输出、专家意见、修复与回归结果。公开仓库只放可分享的方法与脱敏样例。
