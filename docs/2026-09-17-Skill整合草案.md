# LexPrism Skill 整合草案

方案评审版 v0.1｜2026年9月17日。配套 [两窗口工作流方案](2026-09-17-两窗口Skill与自动化工作流方案.md)。以下为下一轮可据以修改的候选文字，不是已部署 Skill；原 `skills/`、程序和技能包本轮均不改动。

## 1. 保留两个 Skill，文件程序承担确定性动作

`lexprism` 负责研究、起草、修订和向律师办理交付；`lexprism-review` 负责另一个实际对话中的独立审阅。共同规则只在生成侧维护源文件，通过现有构建程序同步到审阅包。审阅专用执行顺序保留在 `review-protocol.md`。

不增加面向律师的流程管理 Skill。进入已配置的两窗口工作区后，两个 Skill 通过同一份 `project-collaboration.md` 约定调用项目程序。没有项目程序的通用独立文件任务仍按 `file-delivery.md` 处理，不伪称已登记或已正式发布。

绘图 Skill `drawio-diagram` 继续在实际有图形需求时使用，不因本次两窗口设计改其主体功能。

## 2. 生成入口的拟议调整

保留现有简介、研究方法及按需参考表；替换“处理与交付”的路由，增补正式发布责任。不要把下列文字与旧版冲突条款同时保留。

### 直接开始与路由

> 从自然语言和材料提取本次目的、立场、读者、法域、事实与日期；沿用已确认信息，只追问会影响结果的缺项。简短问题直接回答，不创建事项或成套文件。
>
> 在已配置两窗口管理的项目工作区，成篇起草、合同审查、检索报告、持续修订及提交独立审阅自动使用项目流程。先读取工作区入口并按 `project-collaboration.md` 定位事项；两个窗口使用同一事项，不能为绕过历史新建目录。其他环境的独立文书按 `file-delivery.md` 交付；用户明确要求版本管理或已有事项时沿用项目记录。
>
> 本次是维护 Skill、程序或设计方案时按维护任务处理，不创建虚构客户事项。

### 生成、修订与交接

> 在程序返回的独占副本中工作，按成果用途登记本版主成果、双视图、必要辅助成果、原始要求、证据和修订回应。候选 Word 在送审前生成并完成本任务必要的内容与页面检查，随后封存本版。
>
> 修订时直接读取真实的完整审阅意见。逐项接受处理、提出有证据的异议或说明待补件；协调意见之间的目标冲突，检查修改对全稿及相关成果的影响。生成侧不关闭独立审阅问题。
>
> 提交成功后返回当前稿链接及“请到审阅窗口开始审阅”。文件保存、版本登记和法律内容完成分别说明。另一窗口由律师触发，不自动启动或催办。

### 正式交付

> 律师要求正式交付时，调用实际可用的发布预检，读取最新版本及有效审阅。通过后链接已审候选文件，把尚未确认的项目名、文件名和本次交付范围合并询问。已确认名称不重复询问，律师明确修改时再更新。
>
> 只有律师明确确认确切文件及版本、程序重新核验全部门槛后，才执行正式发布。发布只复制已审、已确认的文件，不重新起草。成功后返回正式文件链接；失败如实说明已确认、文件写入和登记各自的实际结果，保留历史。正式发布只代表本地正式文件生成，不自动发送、签署或送达。

原 `research.md`、`checkpoints.md`、法律报告及合同等路由保留。主要入口不重复铺开发布状态字段、命名算法及全部测试条件。

## 3. 审阅入口的拟议调整

> 律师在本窗口启动审阅后，读取工作区入口及本窗口绑定事项。每次开始均刷新真实状态并固定所审版本；两个窗口不能分别创建本事项。仅审用户提供的独立文件时仍可直接审阅，不强制建项目。
>
> 读取本版完整任务、发布候选文件、要求的双视图、证据及有关成果，按 `review-protocol.md` 完成证据、覆盖、文风和适用的一致性检查。不同用途成果核对共同事实、前提及行动，不要求正文相同。
>
> 写入一份完整独立意见和真实检查范围。区分已证实错误、未核事项和可选表达建议；只基于真实新稿和证据确认问题解决或撤回误报。复审在核销后通读全稿，不以生成侧回应代替复核。
>
> 按共同判定规则给出通过、需修改或待补件。通过后停止本轮，提示律师回生成窗口办理交付；通过仅代表本版独立审阅完成，不替律师批准正式交付，不触发发布。必要事实或材料不足时集中说明待补项与影响，不把未知记成条件满足。

实际对话独立性要求继续保留：同一生成对话切换角色是自检；程序中的不同名称不能证明独立性。

## 4. 新增 `references/lawyer-letters.md` 的候选全文

### 律师函与对外争议沟通

用于律师函、催告函及类似争议沟通。先识别发函主体、收函对象、代表立场和本次沟通目的；事实来源与适用性沿用共同研究规则，不照抄样本的合同事实、律所名称、编号、费用或期限。

#### 围绕本次目的选择内容

先确定希望对方履行、说明、提供材料、安排检验还是参与协商。正文通常依次承担必要事实、合同或法律依据、具体请求、必要后果、权利保留和异议沟通等功能；按实际任务组织，不强制固定标题、页数或段落数量。

内部风险分析可以比较多种主张和救济。对外函件只使用本次目的需要且当前事实与依据支持的部分，不把每条潜在救济和完整要件分析都搬入正文。

#### 事实与主张分别表达

区分委托人陈述、已有材料记载、实际完成的核查以及尚待核实事项。“委托人认为”说明立场，不使事实自动成立；没有取得真实核查结果，不写“经核查”“经内部核查暂未发现”。

争议事实未明时，结合任务选用请求说明、提供材料、安排检验或协商等有条件的表达。主张可以代表委托人的争议立场，但不能补造已履行、已付款、已确认条款或已完成调查。

#### 每项行动与后果有自己的条件

具体请求、费用、风险承担、解除或其他救济分别对应必要事实、依据与条件。存在一条相关法条，不代表所有后果均已成立。“未发现不利证据”不能代替对行动前提的核实；尚未核查、证据冲突、足以支持特定行动的情形分别处理。

期限要说明是合同约定、适用规则还是本函提出的履行要求，保留起算事件及必要的合理性判断。未确定送达日期时不凭空计算具体截止日，不把样本中的天数变成通用法定期限。费用主张对应约定或实际发生、增加、原因等所需证据，不仅凭费用名称提出一概承担。

#### 对外正文与内部准备

称谓及发函主体保持一致，不能在律所代表函中混用委托人自称。内部补件、策略分支、反馈编号和工具说明放核验稿或内部说明；对外正文保留其主张成立所必需的限定，不能以“纯净”为由隐藏实质问题。

风险提示与辅助工具说明按 `delivery-notices.md` 的文种规则安排。需要说明发函前条件时向律师单独说明，不把内部编辑清单留在收函人正文。签名、盖章和已经律师审核的陈述以真实状态为准。

#### 修订后的整体检查

同时检查函件、有关备忘录及行动表。减少未经核实的断言和补充论证必须兼容；补充要件分析不能自动升级结论。修订回应记录受影响的共同事实、主张及条件，以及是否新增承诺、金额、费用、期限或事实。

独立复审按全部意见的目标判断处理是否充分，不因原句删除或局部措辞软化即认定解决；继续检查其他段落是否仍表达相反或更确定的结论。

## 5. 既有参考的定点调整

| 文件 | 拟调整内容 | 不重复增加什么 |
| --- | --- | --- |
| `project-collaboration.md` | 管理工作区中的自动路由、每窗口事项绑定、每次唤起刷新、成果清单、交接和发布；参数从真实程序能力获取 | 不把拟议命令写成当前已可调用，不另起第二套审阅判定 |
| `file-delivery.md` | 普通文件与受管理项目边界；对外主成果和内部说明；送审前固定候选 Word | 不要求短答生成双份正文或技术记录 |
| `drafting-review.md` | 明确同成果双视图与不同用途成果；律师函路由；共同底稿与 Word 对应 | 不重复已有事实来源及全套法源标准 |
| `disputes.md` | 增加未知／冲突／支持特定行动的判断；请求与救济分别核对条件 | 不硬编码汽车、七日或某一费率 |
| `expert-feedback.md` | 本案修订先读完整反馈，协调目标冲突并记录跨文件影响；规则推广仍保留范围与证据 | 不把个案反馈直接变全局规则 |
| `review-decisions.md` | PASS 与确认、发布成功分开；确认绑定实际版本及文件；新增内容复审，未变化的失败重试沿用确认 | 不靠免责声明、次数上限或律师确认消除必要检查缺口 |
| `delivery-notices.md` | 直接落实现有对外文书例外：内部工具说明移出正文，实质限定按读者及用途保留 | 不加入第二套“所有文件必须同样免责”条款 |
| 审阅专用 `review-protocol.md` | 不同成果关系、意见目标冲突、原完整意见、候选 Word 与全稿复审 | 不把正文匹配或文件指纹当成语义通过 |

共同参考用现有 `build_text_skills.py` 同步到两个包，验证所有相对链接；不能只改生成侧而让审阅側沿用旧规则。

## 6. 拟议程序数据约定

这是实现参考，律师无需填写或看到。新增字段需先解决现有单 `pair` 与旧状态兼容，不直接修改旧封存文件。

| 记录 | 必要信息 |
| --- | --- |
| 窗口事项绑定 | 工作区、事项、职责；可用时记录真实宿主会话定位；切换事项要明确 |
| 成果清单 | 成果编号、文种、读者、用途、核验视图、纯净视图、候选文件、是否拟发布、相关成果和证据 |
| 项目与文件名称 | 原始显示名称、实际安全名称、确认情况与时间；内部事项编号保持独立 |
| 律师确认 | 用户原话及实际来源记录、时间、范围、事项、版本、送审包指纹、候选文件指纹、最终名称和目标路径 |
| 发布记录 | 唯一发布标识、所用确认、成果清单、状态、尝试、实际时间、路径、文件指纹、失败或恢复原因 |
| 当前索引 | 最新送审版本、当前有效审阅、最近成功发布版本、未完成发布；由真实记录生成 |

程序不能自行创造真实用户确认或独立会话身份。文件指纹只能识别内容，不证明事实、法律正确性或授权真实性。

## 7. 本轮改动与下一轮边界

本轮实际修改的生产 Skill：**无**。`lexprism`、`lexprism-review`、`drawio-diagram` 均保持现状；没有升级版本、生成新导入包或改写客户事项。

本轮新增本草案、整体方案及配套流程图。后续实施时应集中修改两个文本 Skill、上述共同参考、两层项目模板和文件程序，再同步打包与验收；单独有流程图不能表述为已完成自动化部署。
