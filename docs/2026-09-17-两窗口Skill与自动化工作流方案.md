# LexPrism 两窗口 Skill 与自动化工作流方案

方案评审版 v0.1｜2026年9月17日

本版根据律师函累计复盘、埃及报告复盘、用户提供的自动化总结及当前仓库整理。用户已明确：**先完成方案与流程图；律师手动触发生成、审阅两个窗口，后台自动完成项目文件管理。** 本版没有修改运行中的 Skill、程序或技能包。

## 1. 建议采用的整体方案

保留两个职责入口：生成窗口使用 `lexprism`，审阅窗口使用 `lexprism-review`。两个窗口绑定同一事项，共用一份有版本的档案；每次被律师唤起时，先读取实际状态，再继续自己的工作。后台由现有本地程序扩展承担定位、工作副本、送审、记录、命名和正式发布。

律师日常只需在两个窗口说话、提供材料，并确认项目与文件名称。决定性事实、委托立场和正式交付仍由律师判断；系统应集中询问真正影响结果的问题，不能把这些专业判断折叠进“自动处理”。

这里的“后台”指宿主调用的本地文件程序，不要求增加网页、常驻服务器或第三个操作窗口。文件共享不等于自动启动对话；律师没有触发另一个窗口时，流程正常停在“待审阅”或“待修订”，不自动催办。

“在本地处理文件”指档案、版本及发布文件在授权本地工作区管理，不据此宣称模型推理、法律数据库调用均在本地或离线运行。目标环境中可读取的项目范围、文件工具、Word 能力和法律连接器应在部署验收时实测。

### 三层职责

| 层 | 负责什么 | 律师看到什么 |
| --- | --- | --- |
| 前台：两个对话窗口 | 理解委托、研究起草、独立审阅、解释缺口及结果 | 需求、当前文稿、审阅意见、待补信息、下一步 |
| 中间交接：事项绑定与动作适配 | 把自然语言动作绑定到确定事项和版本，调用程序，读取真实返回结果 | 简短状态，例如“已送审，请到审阅窗口开始审阅” |
| 后台：本地文件程序 | 独占副本、不可覆盖版本、审阅登记、确认记录、发布与失败恢复 | 当前正文或正式文件链接；异常时说明影响及可继续的动作 |

中间交接是 Skill 与本地程序之间的约定，不是需要律师安装、调用的第三个 Skill。

## 2. 复盘后应保留、调整和补上的部分

当前两个文本 Skill 均为 `0.7.1-checkpoints`。当前程序已经实现事项发现、独占副本、成对文件送审、审阅绑定、四维结果登记、历史校验和文件锁。本轮重新运行共享引用检查及现有 29 项测试，均通过。这说明已有功能具备局部验证基础，不证明以下拟议能力已经存在，也不证明千问中的法律质量已经通过。

| 原建议或现有设计 | 本版判断 | 处理方式 |
| --- | --- | --- |
| `matters` 留全过程、`output` 留正式副本 | 保留 | 工作历史和交付文件分开，发布不搬走原档案 |
| 所有成篇工作是否自动建事项 | 在本次两窗口项目工作区内采用自动管理 | 项目入口声明这一约定；通用 Skill 在其他环境仍可处理独立文件；短答始终不建档 |
| 两个窗口共用当前事项 | 必须落实到绑定关系 | 每个窗口保存自己的事项绑定，不能只依赖一个会被其他窗口改写的全局“当前事项” |
| 每次提交都只有两个文件 | 需要澄清 | 两份完整视图属于同一成果；备忘录与律师函是两种成果，需要各自的正文与证据对应关系 |
| 审阅通过后再生成正式 Word | 调整顺序 | 送审时固定候选 Word，审阅及律师确认覆盖这个文件，发布只复制该文件 |
| PASS 即可进入交付 | 保留独立的律师确认 | 审阅、律师确认、发布成功分别记录，旧版确认不批准新稿 |
| 新增脚本 `publish/release` | 确有必要 | 当前同名辅助函数 `publish_directory` 只用于内部封存，不是正式交付动作 |
| 不断向 Skill 追加规则 | 改为有限增补 | 保留 0.7.1 已有质量规则，只补律师函文种、反馈目标冲突、成果关系和发布流程 |
| 律师需要复制反馈或找版本 | 自动化消除 | 两个窗口直接读完整文件；版本、状态、命名处理留在后台 |

## 3. 律师实际走一遍

下表中的状态和话术是拟议体验，不是本轮已完成的客户事项。

| 步骤 | 律师在哪个窗口说什么 | 窗口与后台自动做什么 | 返回给律师 |
| --- | --- | --- | --- |
| 开始 | 生成：“根据这些材料起草律师函，项目叫某某交付争议。” | 定位或创建事项，记录名称，保留原件，确定本次文种、读者及主成果 | 理解的任务；只列会影响起草的关键缺项 |
| 形成送审稿 | 生成：“形成初稿并提交审阅。” | 研究、起草、生成核验稿和候选 Word，自检并封存本版 | 当前稿链接；“已送审，请到审阅窗口开始审阅” |
| 独立审阅 | 审阅：“审阅某某交付争议当前送审版本。” | 首次绑定该事项，以后沿用；锁定当前版本，读取完整稿件、证据及意见历史 | 通过／需修改／待补件，一份完整审阅意见 |
| 修订 | 生成：“按审阅意见修订并提交。” | 读取真实意见，逐项处理或有据异议，检查全稿和相关成果，另存新版本 | 本轮关键变化、剩余缺口及新送审稿 |
| 复审 | 审阅：“复审当前版本。” | 读取新稿、旧意见、修订回应及受影响依据；核销后通读全稿 | 本版结论；通过时提示回生成窗口办理交付 |
| 准备交付 | 生成：“准备正式交付。” | 确认最新版本通过，提出名称和路径，链接已审候选文件 | 一次性确认项目名、文件名、确切文件和交付范围 |
| 发布 | 生成：“确认按上述名称，将这份文件作为正式交付。” | 记录确认，再校验门槛；把已审文件复制到正式目录，登记实际结果 | 成功时返回正式 Word 链接；失败时明确尚未成功发布 |
| 发布后修改 | 生成：“这份函还需要改一处实质内容。” | 从已发布版创建新工作副本，重新送审与确认，新增交付版本 | 新版文件链接；旧交付继续保留 |

两个窗口各自需要真实的首次触发。首个窗口已建立事项后，第二个窗口用项目名称或明确路径绑定；仅有一个候选且与本次任务匹配时可以自动定位。存在多个同名或无法区分的事项才询问选择，不让律师填写内部编号。

建议的交付确认话术：

> 本版已通过独立审阅。请核对这份候选 Word：〔文件链接〕。拟按项目“某某交付争议”、文件“催告提车律师函_v0002.docx”生成正式交付副本。是否确认？

名称已确认且未变化时不重复问名称，只确认本次文件和版本。律师可以一次回复完成命名与发布授权。“可以”“就这版”只有在明确对应眼前的候选文件和范围时才作为确认，不能从沉默、打开文件或经过一定时间推定。

“正式发布”在本方案中仅指生成本地正式交付文件；向客户发送、签署、加盖印章或法律意义上的送达属于后续独立动作，本流程不自动执行。

## 5. 事项和成果怎样组织

### 路由与定位

本次建议在“已配置两窗口管理的法律项目工作区”中自动管理成篇任务。简短问答、少量润色直接完成，不创建事项和正式文件。继续已有事项时沿用其历史；从独立文件纳入项目时保留原文件，记录来源后形成首个受管理版本，不补造过去的审阅。

定位顺序：用户明确路径 → 本窗口已绑定事项 → 授权工作区内登记元数据 → 任务匹配判断。发现损坏状态、权限故障或历史校验失败时报告异常，不把“未读到”当作“没有”而重新初始化。多候选只先读取元数据，不跨客户打开正文寻找线索。

建议默认“一项业务委托对应一个事项”，同一事项可包含若干成果。正式项目名称与内部事项编号分开，项目名称可在开始给定，也可由系统提出暂用名称，交付前确认。大项目包含多个事项时，每次发布必须指定所属事项及输出子目录，不能自动把多个事项合并到一个同名目录。

### 本地目录约定

```text
授权工作区/
├─ PROJECT.md / AGENTS.md       工作区入口与两窗口管理约定
├─ skills/、scripts/、templates/  规则和工具，不放客户材料
├─ matters/
│  └─ 内部事项编号/
│     ├─ PROJECT.md / WORK.md / state.json
│     ├─ inputs/                原始材料及取得记录
│     ├─ drafts/                各窗口独占、尚未提交的工作副本
│     ├─ versions/              不可覆盖的送审包和文件清单
│     ├─ reviews/               独立意见、结论及问题处理历史
│     └─ releases/              拟新增：确认、发布尝试和实际结果
└─ output/
   └─ 已确认项目名/
      └─ 已确认文件名_v0002.docx
```

`output` 默认只增加一份指定主成果的对外文件。附属备忘录、核验说明和审阅意见留在事项中；律师明确要求一并交付时，把指定附件纳入同一次确认及发布清单。机器记录留在事项及工作区内部登记中，不作为客户附件。

### 三种关系必须区分

| 关系 | 例子 | 实际检查 |
| --- | --- | --- |
| 同一成果的两个视图 | 同一律师函的核验稿与纯净稿 | 共同正文、引注、事实限定、金额期限和主张含义一致；核验稿可另有内部说明 |
| 正文与核验说明 | 普通独立文件与简短核验说明 | 每项关键主张可回查，核验说明不必重复整篇正文 |
| 不同用途的成果 | 内部风险备忘录与对外律师函 | 共同事实、条件和行动相容；两者正文、结构及结论详略可以不同 |

本次受管理项目继续支持完整双视图；多成果时以“成果清单”登记每份成果、用途、两个视图及发布选择。不能为了适配现有 `pair` 参数，把备忘录当成律师函的核验视图。具体数据字段和 Skill 文字见 [Skill 整合草案](2026-09-17-Skill整合草案.md)。

证据、共同事实或另一份成果发生改变时，要检查对本次发布文件的影响。默认以整份送审包形成新版本，重新取得覆盖该版本的审阅；不要把“正文看似未变”当成依据变化没有影响。

## 6. 前后台交接约定

下列是拟议能力名称，不是当前可直接执行的命令。

| 交接动作 | 窗口交给程序的关键信息 | 程序返回及保证 |
| --- | --- | --- |
| 定位／绑定 | 授权工作区、已有绑定或用户指定项目、窗口职责 | 唯一事项路径、真实状态和下一步；模糊或损坏时不自动创建 |
| 取工作副本 | 事项、基线版本、生成窗口身份 | 独占目录，写入只在该副本中 |
| 提交送审 | 基线、成果清单、任务、正文、证据、修订回应 | 不可覆盖版本、待审状态；陈旧基线拒绝提交 |
| 开始审阅 | 事项、指定版本、真实审阅窗口信息 | 固定版本及审阅工作区；不读取不断变化的工作稿 |
| 完成审阅 | 完整意见、检查范围、问题及依据、实际执行记录 | 由有效结果汇总当前状态；完成意见不可改写 |
| 准备发布 | 当前版本、发布成果、拟用项目及文件名称 | 已审候选文件、确切输出路径、缺失门槛；只预检，不提前写正式文件 |
| 记录确认 | 用户原话、时间、来源记录、候选文件及交付范围 | 绑定具体版本、文件指纹、名称及目标位置的确认记录 |
| 执行发布 | 已记录确认、预期最新版本、发布标识 | 再检查后复制候选文件、核对指纹、记录路径，成功才返回正式链接 |
| 恢复发布 | 原发布标识及失败记录 | 检查已有结果，同一次成功不重复创建，失败可继续且不改正文 |

每次窗口被唤起都刷新事项状态；窗口聊天里的上一轮总结不是状态依据。程序错误由窗口解释为可理解的结果，不把错误日志交给律师调试，也不通过手改状态让界面显示成功。

程序能够校验文件和记录关系，不能从 `actor` 字符串推断真实独立审阅，也不能从模型生成的一条确认记录证明律师确已批准。应保存实际会话／消息定位或可回查原始记录。目标宿主缺少可自动验证的身份接口时明确这一保证边界，不能把人为填写的名字当成技术认证。

## 7. 法律质量怎样进入工作流

保留三个轻量检查点：范围形成后、关键依据就绪后、完稿送审前及实质修订后。记录后继续工作，默认不逐点要求律师批准。决定性信息只能由律师提供时，集中列明影响并暂停受影响结论，其他明确部分可以继续。

| 复盘问题 | 在哪里处理 | 通过标准 |
| --- | --- | --- |
| 律师函装进整份风险报告 | 新增 `lawyer-letters.md`，起草及文风审阅使用 | 围绕本次发函目的，选择必要事实、依据、请求、后果及异议渠道 |
| “待核”变成“经核查” | 既有事实来源与研究规则，函件指引补具体例子 | 陈述来源、已完成核查及未完成核查清楚区分，不生成不存在的调查结果 |
| 未见不利证据即建议行动 | 在 `disputes.md` 补行动条件 | 尚未核查、证据冲突、足以支持行动分别判断；未知不得作为条件满足 |
| 法条正确但费用、风险、解除一并断言 | 既有适用性规则，争议参考细化 | 每一项请求和后果分别对应必要事实、依据与条件 |
| 一条意见改软，另一条又强化结论 | 反馈和复审规则补目标冲突检查 | 读完整意见，按目标协调；全稿及相关成果一致，不靠追加句子核销 |
| 内部待补事项进入对外正文 | 修订现有正文与交付提示条款 | 内部策略、补件和工具日志独立保存；对外正文仍保留实质限定 |
| 旧问题消失即通过 | 继续执行 0.7.1 全稿复审 | 核销后通读全文；检查新增事实、承诺、费用、期限及相互矛盾 |
| 只有生成侧转述审阅意见 | 项目交接与独立审阅规则 | 保存原始完整意见、所审包及真实执行范围；新版本接受实际复审 |

不同用途成果的一致性是语义判断，不能靠逐字对比替代。程序可辅助寻找冲突和漏项，Skill 执行实际判断，律师负责最终专业确认。人工样本只提取适用的文种经验，不搬用本案没有取得的合同事实、费用标准、律所署名或期限。

## 8. 正式发布的门槛与失败处理

### 发布前检查

1. 目标版本仍是事项最新版本，历史和送审文件未被篡改。
2. 发布清单内的成果完整；本项目要求的完整双视图、依据及回应均已随版本封存。
3. 实际独立审阅覆盖本次任务及发布成果，完整意见可回查；仅做局部校对不能冒充整份验收。
4. 当前版本的全部有效审阅合并结果为 PASS；被明确替代的旧意见保留历史。不能挑一份 PASS 忽略同版 REVISE／PENDING。
5. 没有未解决的阻断问题或未完成的必要检查；取消仍在进行的审阅必须有真实理由并保留记录。
6. 没有仍在进行中的当前版本审阅。
7. 律师明确确认确切版本、文件及交付范围，确认未撤回且文件未变化。
8. 项目名和文件名已确认；名称、所属事项和目标目录关系明确。
9. 目标在授权 `output` 内，目录属于本事项，既有文件不被覆盖，目标格式可正常生成和检查。

程序与 Skill 分担门槛：程序核查结构、状态、绑定和路径；Skill 执行并如实记录法律内容、范围和页面等检查。必要检查没有做完时，不能用“由律师最后确认”代替，再登记通过。

### 先固定文件，再审阅和确认

送审阶段即产出候选 `.docx` 并检查正文、脚注、表格、分页等实际要求，封存后由审阅窗口读取。准备发布时链接这份候选文件；发布仅复制同一文件并验证一致性，不再次调用模型改写、不重新套模板或加入新署名。

如必须转换格式，转换后的文件仍是候选文件，须完成与已审内容的对应检查及本任务必要的页面核验，之后才能确认发布。出现实质改动则生成新版本并复审。无法生成或完成必要页面检查时，交付当前草稿并说明限制，不假称正式 Word 已完成。

### 名称、并发和恢复

项目及文件名称保留显示值与实际文件系统值。拒绝空名称、`.`、`..`、路径分隔符、控制字符、Windows 非法字符及保留设备名；处理末尾点／空格、长度和大小写等价冲突。不能静默删除字符使两个名称落到同一路径。明显规范化时给出准确建议，随交付名称一起确认。

输出目录绑定事项所有者；同名目录属于另一事项或归属不明时不合并覆盖，提出带区分信息的新名称。检查解析后的路径及目录链接，防止符号链接或 Windows 目录联接跳出授权范围。重命名后的新目录也要做同样的检查。

发布使用事项锁及输出目标锁，锁内再次核对版本、审阅、确认和路径。先在受控临时位置复制并核对，最后以不覆盖方式落盘。跨 `matters` 与 `output` 的操作可能中途失败，应保留发布意图、尝试及实际文件结果，不能假定两处写入是一个原子动作。

| 情况 | 系统处理 | 律师看到 |
| --- | --- | --- |
| 未审、需修改、待补件或审阅中 | 拒绝正式发布，保留现稿并给出具体下一步 | “当前尚不满足正式交付条件”及原因 |
| 确认后产生新版本、文件变化或新审阅推翻通过 | 原确认不能用于新内容；按实际变化重新审阅／确认 | 新版或新问题的具体影响 |
| 名称冲突／目录不明 | 提出不冲突的名称，不覆盖、不自行合并事项 | 一次名称选择 |
| 已确认但复制失败 | 保留确认和发布尝试，后续触发时重新检查条件后重试 | “已确认，尚未成功发布”及原因 |
| 文件落盘、登记失败 | 标记发布结果待核对，恢复时校验归属与指纹后补登记，不重复发布 | “文件已写入，交付登记尚未完成” |
| 同一发布请求重复执行 | 已成功且文件一致则返回原文件；不生成另一份“最终版” | 原正式文件链接 |
| 已交付内容需实质修改 | 新工作副本→新版本→独立复审→重新确认→新增正式文件 | 新版链接，旧版及旧确认记录保留 |

单纯失败后的重试，在版本、文件、审阅、名称与确认范围都没有改变时沿用原确认；情况改变则说明变化并取得相应确认。发布记录的失败状态不能回滚或删除已存在的送审及审阅历史。

工作状态、审阅结论、律师确认和发布结果分别记录：一份历史文件已经发布，与当前新稿待审可以同时成立。“最新送审版本”与“最近成功发布版本”是两个字段，不能用一个“已完成”覆盖全部状态。

### 关键验收情景

- 短问答不建事项；两窗口对同一任务绑定同一事项；多个候选先选择，损坏历史不触发重建。
- 律师不复制审阅意见，生成侧读到完整审阅全文；重开窗口能继续；另一个窗口未触发时保持等待。
- 陈旧基线、提交文件被改、历史意见被改均不能静默继续；旧 PASS 不能批准新稿，未完成审阅阻止发布。
- 无审阅、REVISE、PENDING、范围不足、阻断未关闭、缺必要检查、缺确认或名称时不能发布。
- 同一成果的双视图保持实质一致；备忘录与函件按事实、条件、行动相容性检查；发布清单只含所选对外成果。
- 发函事实未核时不生成“经内部核查”；软化事实必须传导到结论和行动；没有不利证据不能代替行动条件。
- 补论证不升级结论；补期限、费用、主张或事实必须检查新增依据；独立复审不能只看旧问题是否消失。
- Word 在送审前固定，必要页面检查真实完成；最终副本与已审、已确认文件逐字节一致。
- 路径穿越、Windows 保留名、末尾点空格、目录链接、大小写冲突、跨事项同名、重复发布、并发发布分别测试。
- 已确认后写入失败保留确认与历史；落盘后登记失败可恢复；重试不重复创建；实质修订新增版本并保留旧交付。
- 千问中实测两个窗口能访问同一授权目录、读取项目入口、执行文件程序并打开返回的 Word；无自动唤起也完整走通流程。

本轮完成的是设计与现有基线检查，没有执行以上新增能力的验收，没有重跑法律案例，也没有创建客户正式交付物。
