# LexPrism 项目协作操作说明

## 律师的操作

准备一个独立事项目录，让两个对话都在这个目录下工作。律师向生成对话说明“根据本项目材料生成文稿并提交审阅”，向独立审阅对话说明“审阅本项目当前送审版本”，需要修订时启动生成对话说“按项目里的审阅意见继续修订”。文件和意见由对话自己读取，不需复制粘贴。

项目完整包包含三个技能：文本生成 lexprism、文本审阅 lexprism-review、生图 drawio-diagram，以及项目指令、版本程序和绘图工作台。按宿主方式安装或加载所需 skill；仅有目录不证明自动触发成功。初始化后事项根目录含 AGENTS.md 和 PROJECT.md，从此目录启动支持项目指令的宿主；其他宿主按其真实项目指令入口加载 PROJECT.md。

drawio 是项目组成部分，沿用现有版本和规则，维护重点仍放在文本流程。完整包提供 tools/drawio/index.html、两份图形模板、现有生成／静态核验脚本及图表计划模板。工作台页面会加载 embed.diagrams.net 在线编辑器，打包本地页面不等于提供完整离线编辑器。生成脚本包含示例数据，实际案件必须依据已核验材料替换，静态检查通过不代表法律内容和渲染效果均已审阅。

初始化程序只复制项目指令和文稿版本工具，技能按宿主安装；绘图工作台从解压包的 tools/drawio/index.html 打开。事项目录与解压包目录不同就使用实际绝对路径。图形工作副本放 drafts/<编号>/files/drawings，随相关双文件提交进入同一版本；后续修改新副本，保留已提交图形历史。

## Agent 的具体操作

以下命令由 Agent 根据实际路径和对话标识填写并执行，律师无需记忆。项目包的结构为 scripts、skills、templates 及本说明；初始化用包内 scripts/document_workflow.py，后续使用复制到事项根目录的 document_workflow.py。Python 3.10 及以上，仅标准库；本地测试环境为 Windows / Python 3.14。

```text
python scripts/document_workflow.py --root <新事项绝对路径> init --matter-id <事项标识>
python <事项根目录>/document_workflow.py --root <事项根目录> status
python <事项根目录>/document_workflow.py --root <事项根目录> checkout --actor <生成对话实际标识>
```

checkout 返回工作副本编号和 files 路径。生成侧在该 files 中保存：

- verification.md／verification.docx 等核验草稿文件；
- clean.md／clean.docx 等纯净展示文件；
- BRIEF.md：原始要求、有效补充要求、事实前提、范围、法域、基准日、来源限制及偏好；
- RESPONSE.md：本轮变化、逐项意见回应；首稿明确写首稿，无上一轮意见；
- evidence：本次依据快照、原文片段、来源定位和授权内必要附件。首次无外部材料的纯整理任务也应在 BRIEF.md 说明来源范围，不伪造材料填目录。

```text
python <事项根目录>/document_workflow.py --root <事项根目录> submit --draft <工作副本编号> --verification verification.md --clean clean.md
python <事项根目录>/document_workflow.py --root <事项根目录> start-review --actor <审阅对话实际标识>
```

送审文件名按实际格式填写。start-review 返回 review 编号和目录；审阅侧先读取 versions 中该版本的实际双文件与材料，再填写本轮 REVIEW.md 和 result.json。结构化结果四个检查键固定为 evidence、coverage、prose、views，每项要有状态和实际依据／限制描述；execution_ref 填能回查的真实对话执行记录，不用自填报告 ID 冒充证明。

一条审阅意见的记录示例（仅字段示意，不能原样当实际审阅提交）：

```json
{
  "id": "I001",
  "blocking": true,
  "status": "OPEN",
  "anchor": {
    "version": "v0001",
    "file": "clean.md",
    "section": "第二节第二段",
    "exact": "从原文复制的待审句子",
    "prefix": "用于消歧的前文",
    "suffix": "用于消歧的后文"
  },
  "reason": "具体问题及证据",
  "requested_change": "要求怎样修改或补件",
  "acceptance": "复审如何确认解决"
}
```

全文结构问题可用 anchor.scope="document"，仍须指定 version 和 file。Markdown 等文本的原句和上下文需要唯一匹配；Word 文件的定位由审阅者实际提取和预览，不声称程序完成 Word 批注锚定。跨版本沿用问题编号时更新锚点、记录原问题关联，不自动将位置漂移视为问题消失。

```text
python <事项根目录>/document_workflow.py --root <事项根目录> finish-review --review <审阅编号>
```

程序根据四维状态、未完成检查和阻断问题计算本轮结论。所有完成审阅中仍有效的结果共同决定当前状态；另有正在执行的当前版审阅时仍为 IN_REVIEW。报告正文应与程序最终登记一致；不能手写“通过”覆盖未完成的检查。

生成侧下一次启动直接读 WORK.md、完整审阅报告及 result.json，checkout 新工作副本，逐项修订并 submit；旧版 PASS 不自动继承。当前版已经 PASS 则停止修改循环，单独记录实际律师确认，不为更新状态而改送审文件。

## 并发、取消和恢复

- 两个生成对话从同一基线开始，先提交者成功，后提交者必须读取新版本并整合；不要手改 draft.json 或 state.json 绕过检查。
- 需要恢复旧内容时用 checkout --from-version <旧版本>，生成新的工作副本及后续版本。新版本仍需审阅，历史不删除。
- 已停止的审阅可用 cancel-review --review <编号> --reason <实际取消原因> 取消，工作记录保留。先确认对应对话已经停止，不为跳过不利意见取消正在进行的必要审阅。
- 同一版本的旧审阅判断需要纠正时，新开审阅，在结果的 supersedes 列出旧编号、supersedes_reason 写实际理由。旧结论和原文不改；不能以“更正意见”隐藏实际新增／变更的依据，依据包改变须提交新文稿版本。
- .workflow.lock 是短时登记锁。遇到锁先查看进程是否仍运行；不能只按经过时间强删。确认进程退出后可清理这一锁文件并运行 status。该操作不允许删除版本目录。
- 中断留下 .pending-* 或尚未登记的版本目录时，保留并核对 state.json、文件清单和实际执行结果。只有登记的版本才是当前版本；未登记目录不批准、不覆盖，可重新提交使用新编号。审阅 final 已生成但尚未登记时，保存记录、取消原未完成审阅并新开一次完成核查，勿覆盖 final。
- WORK.md 损坏可用 status 从登记与已校验文件重建。state.json 或已封存历史损坏不能由 WORK.md 反推修复，需从可靠备份恢复并重新核对。

## 能力说明

程序保存成对快照、证据和独立审阅记录，检查基线／哈希，自动生成工作索引与可解码文本差异；不使用 Git，不联网、不调用模型，不自动唤醒另一对话。它不自动判断法律正确性、不生成 Word 原生红线、不认证对话身份，也不提供企业存储权限与防篡改归档。实际宿主的共享目录、指令加载、脚本能力及法律工作质量需分别验证。
